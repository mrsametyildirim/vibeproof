# Supabase

The single highest-yield area in this whole tool.

Analyses of apps generated by AI builders repeatedly find **row-level security
disabled on at least one table in the large majority of them**, and the exposure
class was significant enough to receive a CVE (CVE-2025-48757, disclosed 2025).

The reason it happens is structural, not careless. A table created by raw SQL, by a
migration, or by an AI builder has **no** row-level security until someone enables
it. Nothing fails. Nothing warns. The app works perfectly, because the developer is
logged in as themselves and every row they can see is theirs.

And when RLS is off, this is what the anon key is:

> A full read and write key to that table, shipped to every visitor of the site.

The anon key is *supposed* to be public. Row policies are the only thing standing
behind it. Without them, "the anon key is public by design" stops being reassuring
and becomes the whole problem.

## The four states

Do not report "RLS" as one thing. These are different findings with different
severities, and only the first two are usually recognised.

### 1. RLS disabled — `VP-SB-001`

```sql
create table profiles (
  id uuid primary key,
  user_id uuid references auth.users,
  email text,
  phone text
);
-- no `alter table ... enable row level security`
```

🔴 CRITICAL. Every row is readable and writable by anyone holding the anon key,
which is everyone.

Check every table in migrations for a matching `enable row level security`. A table
that appears in migrations and never in an `enable` statement is the finding.

### 2. RLS enabled, policy permits everything — `VP-SB-002`

```sql
alter table profiles enable row level security;

create policy "public read" on profiles
  for select using (true);
```

🔴 CRITICAL, and **more dangerous than state 1** because it looks solved. RLS is
on, a policy exists, a dashboard shows green. `using (true)` means the policy
matches every row.

Variants that mean the same thing: `using (auth.role() = 'authenticated')` with no
ownership term — any logged-in user reads every row; and `to public` on a table
holding user data.

### 3. RLS enabled, policy scoped — but leaking columns — `VP-SB-003`

```sql
create policy "read own" on profiles
  for select using (auth.uid() = user_id);
```

Correct for rows. Now ask what the row *contains*. A `profiles` table holding
`email`, `phone`, `stripe_customer_id` or an address is fine here — the policy
scopes it. But a table people are meant to browse:

```sql
create policy "anyone can read listings" on listings
  for select using (true);
```

is correct *if* `listings` holds listings, and is a PII disclosure if it also holds
the seller's email and phone. Read the column list, not just the policy.

🟠 to 🔴 depending on what is actually exposed.

### 4. RLS scoped for `select`, missing for the rest — `VP-SB-004`

The one that is almost always missed:

```sql
create policy "read own" on projects
  for select using (auth.uid() = user_id);
-- no insert / update / delete policy
```

Policies are per operation. Reading is protected. Then check what the app actually
does — if it deletes, and no delete policy exists, the operation fails closed
(good, but the feature is broken — that is a **reality** finding, not a security
one). If a permissive delete policy exists, it is a security finding.

Enumerate `select` / `insert` / `update` / `delete` per table and say which are
covered. That table is more useful than any prose.

## Storage

Buckets are private unless someone made them public, and AI builders make them
public because that is what makes the image finally appear.

```sql
insert into storage.buckets (id, name, public) values ('uploads', 'uploads', true);
```

Public is not automatically wrong. It is wrong for the wrong contents:

| Bucket contents | Public is |
|---|---|
| Marketing images, public avatars, a CDN | fine |
| Invoices, identity documents, contracts, medical or legal files | 🔴 CRITICAL |
| User photo uploads | 🟠 — object URLs are guessable and EXIF carries GPS |

A private bucket still needs policies. Private with no policy scoping objects to
their owner means any authenticated user can read any object.

Trace what the upload path actually writes into the bucket before deciding. The
bucket name is a hint, never the evidence — `uploads` tells you nothing about
whether those uploads are passports.

## service_role

Covered in `secrets-and-egress.md`, restated because it is the worst case:
`service_role` **bypasses every policy above**. One occurrence behind a public env
prefix makes this entire file irrelevant.

Also check server-side usage. A server route that uses `service_role` for
convenience — because RLS was "getting in the way" — has silently opted that whole
route out of every protection, and it is now the route's own job to check
ownership. It almost never does.

## Before reporting any of this

The [negative-proof](negative-proof.md) requirement applies with full force,
because migrations are not the only place policies live:

- policies created through the Supabase dashboard exist in the database and appear
  in **no file in the repository**
- a later migration may enable RLS on a table an earlier one created
- `supabase/seed.sql`, `schema.sql`, or a dumped schema may carry them
- a separate infrastructure or IaC repository may own them
- generated types (`database.types.ts`) tell you tables exist, never what protects
  them

If the repository contains migrations at all, absence of an `enable` statement is
meaningful evidence. If it contains no migrations — a dashboard-managed project —
then **you cannot see the policies**, and the honest output is:

```
⚠️ UNVERIFIED   Row-level security could not be checked: this project has no
                migrations in the repository, so policies live only in the
                Supabase dashboard.
```

That is an `INCONCLUSIVE` input, not a finding. Declaring RLS missing because the
repository does not contain it is exactly the error `negative-proof.md` exists to
prevent — and here it would be a loud, frightening, wrong CRITICAL.

## Firebase, briefly

The same shape with different names. `firestore.rules` / `storage.rules`:

```javascript
allow read, write: if true;                    // VP-SB-002 equivalent
allow read, write: if request.auth != null;    // any signed-in user, every document
```

The correct form scopes to the owner:

```javascript
allow read, write: if request.auth.uid == resource.data.userId;
```

Default-deny is the absence of a rule, so an unlisted collection is closed — the
opposite of Postgres, where an unprotected table is open. Do not carry the Supabase
intuition across.
